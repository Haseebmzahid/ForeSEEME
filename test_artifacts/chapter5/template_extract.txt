392: Requirement Identifying Technique
393: This section describes the technique used to identify and document the functional requirements of the system.
394: For this project,  Mockup-Based Requirement Analysis  is used. In this approach, user interface mockups are created using UI/UX tools such as Figma, Adobe XD, or Balsamiq. These mockups visually represent how users will interact with the system. Functional requirements are then derived from each screen’s elements and behaviors.
395: Steps to Follow:
396: Identify key features and break them down into individual  screens .
397: Assign a  Mockup ID  to each screen (e.g., M1 for Login Page, M2 for Dashboard).
398: Create  mockups  of the screens using any UI/UX design tool.
399: Identify  interactive elements  on each screen (buttons, forms, menus, etc.).
400: Derive a functional requirement from each element, describing what the system should do in response.
401: Organize all functional requirements using the table format provided in Section  2.2.1 .
402: Backend Process Requirements
403: While mockups are effective for capturing  frontend interactions , some system functionalities take place entirely at the  backend   (e.g., order processing, payment gateway callbacks, email/SMS notifications, scheduled jobs, data validation, account security, and real-time tracking in ride-hailing apps). In addition, there are systems that operate almost entirely at the backend with  minimal or no user interface, such as traffic signal control systems or industrial monitoring systems.” .
404: To capture these processes, the  Event–Response Table  technique is used.
405: It is effective for  modelling  backend or real-time system  behaviours  where user interface interactions are not directly involved.
406: It describes the system’s response to specific events, often including conditions under which different actions occur.
407: This ensures backend workflows are captured in the requirements phase without going into design-level details.
408: For detailed guidelines and examples of both Mockup-Based Requirement Analysis and Event–Response Tables, please see  Appendix A.
409: Functional Requirements
410: This section describes the functional requirements of the system derived from user interactions and mockups. To ensure clarity and maintain a stable specification, each requirement should be documented at the  feature level  (e.g.,  User Sign-In, Product Checkout ), with optional reference to the specific UI element(s) from which the feature is derived.   Each functional requirement must include:
411: A  unique identifier  (e.g., FR1.1, FR1.2).
412: A  clear and  testable  requirement   statement  written at the feature level.
413: A reference to the  originating mockup screen and (if needed) the UI element that demonstrates the feature.
414: An  optional Business Rule , if the behavior is governed by a domain-specific policy, condition, or constraint.
415: Where applicable, Business Rules help clarify why a requirement must behave in a certain way and ensure that system behavior aligns with organizational rules, legal constraints, or client policies.
416: Recommended Format:
417: Use the following table structure to document mockup-based, feature-level functional requirements:
418: Table 2.1 : Mockup-Based Functional Requirement Template
419: Feature (derived from UI) Functional Requirement (FR-ID: Statement) Business Rule [Element e.g.,  User Sign-In ] FRx.y : The system shall [describe expected behavior or action]. [Any business rules if applicable]
420: Examples of this technique are provided in  Appendix A .
421: Non-Functional Requirements
422: This section specifies non-functional requirements (NFRs) other than constraints (recorded in Section 2.3) and external interface requirements (described in Section 7). Non-functional requirements define the quality attributes of the system, such as reliability, usability, performance, and security. To avoid vague statements, these requirements must be written in  specific, quantitative, and verifiable terms  (e.g., using percentages, thresholds, or time limits).
423: 
424: To learn how to write non-functional requirements in measurable ways, students should refer to  Chapter 14 “Beyond Functionality” , which provides practical guidelines and examples of quality attribute requirements.
425: Reliability  
426: Requirements about how often the software fails. The measurement is often expressed in MTBF ( mean  time between failures). The definition of  failure  must be clear. Also, don't confuse reliability with  availability,  which is quite a different kind of requirement.  Be sure to specify the consequences of software failure, how to protect from failure, a strategy for error detection, and a strategy for correction.

437: Security  
438: One or more requirements about protection of your system and its data. The measurement can be expressed in a variety of ways (effort, skill level, and time) to break into the system.  Do not discuss solutions (e.g. passwords) in  the  requirements document.

1183: Appendix D
1184: General Coding Standards & Guidelines
1185: Follow a consistent variable naming convention throughout the code. E.g.
1186: Snakecase  (words are delimited by “_”  like:   variable_one )
1187: Pascalcase  (words are delimited by capital letters like:  VariableOne )
1188: Camelcase  (words are delimited by capital letters except the initial word like:  variableOne )
1189: Hungarian Notation (describes the variable type or purpose at the start of the variable name like:  arrDistributeGroup )
1190: Use naming that visually describes scope like  privateField , Const  etc
1191: Use read only/immutable when a field’s value should not be changed after initialization
1192: Use only get, for properties that should not be updated from outside
1193: Name functions according to their functionalities.
1194: Insert appropriate comments to make the code understandable to any reader. Additionally follow a consistent style to do so. E.g.
1195: /* the below function will be used for the addition of two variables*/
1196: int  Add(){
1197: //logic of the function
1198: }
1199: Avoid commenting on obvious things
1200: Make use of indentation for indicating the start and end of the control structures along with a clear specification of where the code is between them.
1201: Follow consistent naming convention for files and folders. 
1202: Follow proper structure for classes
1203: Group code entities logically into projects/packages/modules/folders
1204: Separate logical layers of application into different modules/services/utilities etc.
1205: User separate files for each class,  struct , interface,  enum  etc. Name of the file and the  enclosing  entity must be same. E.g., class Employee in  Employee.cs /Employee.java
1206: Define and use everything within the minimum scope possible
1207: Use proper access modifier for all code entities if required
1208: Code entities should have maximum cohesion and least coupling possible.
1209: Follow DRY law.
1210: Do not repeat code.
1211: A piece of knowledge should exist only in one place within the codebase/application
1212: Reuse code as much as possible
1213: Always write short methods
1214: Single method should not have too  many  logic, long conditional flow or too many parameters
1215: Strictly follow Single Responsibility Principle (SRP) when writing methods, classes, modules, projects, packages, or any other code entities.
1216: Write classes and other code entities that are easy to extend without modification.
1217: Handle exceptions
1218: Log exception and other significant event details
1219: Follow a consistent convention for logging all over the application

# ForeSeeMe privacy and data handling draft

This engineering draft describes the checked-in application and backend. Before publication, the project owner must confirm the deployed configuration, approve the policy, and obtain qualified Pakistani legal review.

The [verification and closure report](MODULE_9_VERIFICATION_AND_CLOSURE_REPORT.md) tracks unresolved device storage, session revocation, Firebase configuration, and production transport evidence. Firebase Auth logout requests refresh-token revocation. Protected Firestore and admin API paths separately check a session cutoff when applicable. Cached client data and provider endpoints outside that cutoff have different lifecycles. The Android token-storage requirement remains subject to supervisor or instructor decision. Review these distinctions when approving the privacy notice and user-facing logout wording.

| Data | Use and storage | Access and external processing |
| --- | --- | --- |
| Account UID, email, display name, provider identity, credentials and enrolled factors | Firebase Authentication and Google Sign-In support account access and recovery. Firestore holds a separate directory projection for authorized operations. The application passes passwords to Firebase Authentication over TLS. | Firebase Authentication processes authentication data. Google Sign-In processes federated identity. The project does not implement its own password storage. MFA-authorized operators can read the directory, with account administration mediated by the audited API. |
| Profile city and self-reported chronic condition categories | Firestore health profile supports city-level risk display, alert targeting, and relevant health information. Supported categories are asthma, diabetes, hypertension, heart disease and none. | The signed-in owner can read and manage the record. The alert dispatch identity reads the city and categories for targeting. Operators receive profile completion status through a field-masked projection. |
| Medication and adherence | Firestore stores user-entered medication names, dosage, reminder schedules and dose statuses. The app uses these to show medication history and schedule on-device notifications. | The owner accesses the records. Medication notifications can expose names and schedules on the lock screen depending on device settings. Local preferences retain scheduling identifiers, celebration milestones and ordinary UI settings. Review device cache and reminder retention and cleanup before public rollout. |
| Alert preferences, registration token, inbox and dispatch outcomes | Firestore stores notification settings, one FCM registration token per user document, in-app alerts and service-only delivery records. FCM processes registration tokens and alert content for delivery. | Push payloads use city-level environmental information, recommendation text and routing identifiers. Target selection can depend on self-reported categories. Mobile OS notification services can display delivered payloads. Local reminders are generated separately on the device. |
| Disclaimer and revocation records | Firestore stores an immutable, account-bound acceptance record per displayed version and a backend-written session cutoff per user when applicable. | Users can read their own acceptance records. Cutoff records are service-owned. The medical disclaimer covers the scope of the app. Collection of additional clinical data requires separate, explicit informed consent. |
| Device location and nearby hospitals | When requested, the app uses device coordinates or a selected city centre to search Google Places for nearby hospitals. Location lookups are cached in process memory. | Google Places receives search coordinates, radius and facility type. The Google Maps SDK or Google Maps directions link processes coordinates needed for display or directions. The Places request does not include a ForeSeeMe user UID or profile categories. |
| Environmental data and educational sources | Backend jobs request weather and air-quality data from Open-Meteo using configured city coordinates and date ranges. The backend stores city-level risk estimates in Firestore. | Open-Meteo receives city/date acquisition parameters. Email invitation/reset processing uses Firebase Identity Toolkit. Opening cited resources transfers ordinary browser request information to the relevant destination. The Google button graphic is loaded from Wikimedia and can disclose browser or connection metadata to that host. |
| Administrative and operational records | Firestore holds account operations, activity logs, job heartbeats, rate counters and project metrics. Deployment logs may contain operational metadata. | MFA-authorized administrators and designated runtime or operator identities have access according to rules and IAM. Confirm log sinks, retention, processor terms, and incident access in each deployed environment. |

Firestore applies authenticated owner rules to user data and protects administrative collections with role and second-factor checks. The service SDK bypasses Firestore rules under its IAM identity. Role grants, runtime permissions and support access therefore require separate operational review. The application schema has no diagnostic symptom intake, clinical test result upload, or medical record import. Medication names and dosage remain free text for their stated purpose. Expanded collection requires an approved specification, an explicit informed-consent flow, and published handling rules before release.

A future feature must describe the added fields, specific purpose, recipients, retention and withdrawal process before requesting consent. Record the account, feature, approved notice version and server-confirmed timestamp. Keep the feature's collection and processing disabled at the applicable API and Firestore boundaries until a valid record exists. Declining or withdrawing the optional consent must leave the existing product features available, with previously collected material handled under the approved deletion and retention policy.

The source contains no data sale or advertising-sharing workflow. The project owner must confirm actual disclosures and contracts, review whether services acting as processors are consistent with the SRS/SDS third-party wording, and approve any international transfers after confirming locations and applicable rules. Review cloud region, backups, exports, service identities, monitoring sinks, and vendor subprocessors using the deployed project inventory.

The current admin deletion action deletes the Auth account but deliberately retains Firestore records after operator confirmation. The privacy owner must define user access, correction, deletion and consent withdrawal processes, including ownership verification, retention for active/deleted accounts, backup expiration, audit/security exceptions, legal holds and processor deletion commitments. Confirm an operator and user contact channel, incident triage owner, escalation contacts, access-change and security-event procedures, and applicable notification duties with legal counsel. Retention periods, operator identity, international transfers, and legal commitments are pending confirmation and qualified legal review.

Confirm the push-registration lifecycle on shared devices. Firebase Auth logout and FCM registration have separate lifecycles, and a saved token can continue receiving pushes after local logout until its association or registration changes. Review the dispatch ledger retention design alongside the deployed TTL and backups. [Firestore lifecycle design](firestore_lifecycle.md)
